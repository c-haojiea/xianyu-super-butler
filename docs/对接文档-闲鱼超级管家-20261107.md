## 2. 仓库与分支模型

- `main` 是唯一集成分支，始终与 `origin/main` 齐平。
- 任何人改代码：**从 `origin/main` 建 `feat/xxx` 或 `fix/xxx` 分支**，不要直接在生产目录的 `main` 上改。
- 合并方式：rebase 到最新 main 后快进合并（`git merge --ff-only`），或走 GitHub PR。
- `upstream` 只用于同步作者更新，**永远不要向 upstream push**。
- 作者更新时的同步方式：

```bat
git fetch upstream
git switch main
git merge upstream/main        :: 产生冲突时，优先保留我们的本地补丁，再手工重放
```

> 注意：`XianyuAutoAsync.py` 里有本地补丁（见第 3 节），上游合并会覆盖，必须重新应用并在提交说明里写明。

## 4. 提交代码标准流程

### 4.1 提交前自检（缺一项都不算完成）

```bat
:: Python 改动
E:\Cyuyan\Python\Python3.12\python.exe -m py_compile 改动的文件.py

:: 前端改动（dashboard/app.js）
node --check dashboard\app.js

:: 确认没有夹带敏感文件
git status --short
```

敏感文件清单（**永远不要提交**）：`rescue_config.json`、`data\**`、`logs\**`、`*.db`、`config.local.yml`、任何带账号密码的配置。

### 4.2 提交信息规范

- `feat: 新增 xxx`
- `fix: 修复 xxx`
- `chore: 运维脚本/配置调整`
- `docs: 文档`
- 说明写「为什么」，不写「改了哪一行」（diff 自己会说话）

### 4.3 分支与推送

```bat
git switch -c fix/xxx origin/main
:: 改动
git add 具体文件1 具体文件2
git commit -m "fix: ..."
git pull --rebase origin main
git push -u origin fix/xxx
```

### 4.4 合并

- 有权限：维护者执行 `git switch main && git merge --ff-only fix/xxx && git push origin main`
- 无权限：发 PR，或在回报里附 `git format-patch origin/main`

### 4.5 回滚

优先 `git revert <hash>` 生成反向提交，不要 `reset --hard` 改写历史；已推送的提交禁止 force push。

## 5. 红线（改代码前必须知道）

1. **不要写 `data\xianyu_data.db`**：看板、状态检查、巡检都是只读消费；手工修数据必须先停服务、先备份。
2. **不要动 8081（管家）与 8092（看板）端口**：看板端口可用环境变量 `XY_DASHBOARD_PORT` 临时覆盖，但不要改默认值。
3. **不要给账号配置 `username/password`**：密码登录会触发滑块/人脸验证，实测会卡死并占用滑块槽位（见第 8 节）。
4. **不要批量调用评价/求花接口**：一次几十条会触发「账号使用环境存在风险」，导致私聊限制 24 小时。
5. **不要 `git add -A` / `git push --force`**。
6. **不要直接修改 `upstream`**。
7. **看板改动不要引入 CDN/第三方库**：必须离线可用，ECharts 已本地化在 `dashboard\assets\`。
8. **bat 文件必须是 UTF-8（无 BOM）+ CRLF**，否则 cmd 会把行拼在一起报 `'口即停止服'cd' 不是内部或外部命令`。

## 7. 数据接口契约（供「作战计划」读数据）

### 7.1 直接读库（推荐给离线分析）

- 路径：`data\xianyu_data.db`
- 只读连接示例：`sqlite3.connect("file:<路径>?mode=ro", uri=True)`
- 关键表：
  - `orders`：`order_id, item_id, buyer_id, chat_id, amount, refund_fee, order_status, created_at, system_shipped, cookie_id`
  - `item_info`：`item_id, item_title, item_price, listing_status, created_at, cookie_id`
  - `cards`：卡券库存；`item_delivery_configs`：发货规则
- 状态口径：
  - **有效订单**：`completed` / `shipped` / `pending_ship` 且 `amount > 0`
  - 排除：`cancelled`、`unknown`、`created_at` 非 `YYYY-MM-DD HH:MM:SS` 的行
  - 待发货：`order_status='pending_ship' AND system_shipped=0`
- 金额：`amount` 是买家实付，未扣平台服务费；`refund_fee` 是退款额
- 时区：`created_at` 是本地时间，不要用 UTC 做「今天/本月」判断

### 7.2 看板 HTTP API（推荐给在线看板/程序）

先起看板（或常驻），然后：

| 接口 | 说明 |
|---|---|
| `GET /api/dashboard` | 一次返回全部数据，约 135KB |
| `GET /api/health` | 存活检查 |
| `GET /api/export/orders.csv` | 全部订单 CSV（UTF-8 BOM + CRLF，Excel 直接打开不乱码） |
| `GET /api/export/products.csv` | 商品汇总 CSV |

`/api/dashboard` 顶层字段：

```
generated_at, summary, calendar, hourly, products, insights, categories, orders, recent, refunds, weekly
```

常用字段：

- `summary`：`today_revenue/today_orders/today_buyers/today_aov`、`month_*`、`last30_*`、`pending_count`、`total_*`、`repeat_rate`、`net_revenue`、`cancel_rate`、`spark`
- `calendar.days[]`：`date, revenue, orders, cancelled_orders, refund_orders, refund_value`
- `products.all[]`：`id, title, category, orders, revenue, buyers, repeat_buyers, active_days, first, last, avg_amount, orders_7d, orders_30d, velocity, share, listing_age_days, daily[]`
- `insights`：`hot[], cold[], time[], overall[]`
- `categories[]`：`name, orders, revenue`（含兜底的「未识别商品」）
- `orders[]`：`date, time, item_id, title, amount, status`
- `refunds`：取消/退款/净收入与按商品归因
- `weekly`：本周与上周同期对比

### 7.3 使用注意

- 看板是**按需启动**的，不常驻；作战计划不要假设 8092 一定在。
- 看板只读，不会影响自动发货；但**不要在看板运行时对同一 DB 做长时间写事务**。
- 看板右上角 `LIVE` 只代表看板服务活着，不代表管家在线。判断账号是否在线看 `logs` 的 `handle_heartbeat_response` 最近时间，或跑 `检查运行状态.bat`。

## 8. 已知坑（历史踩过，改代码前先看）

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 企业微信只收到 1 条「Token 异常」然后静默 | `_notify_relogin_required` 是一次性通知（`_relogin_notification_sent`），防刷屏 | 不能拿「没再提醒」当恢复证据，必须看心跳/日志 |
| 2 | 账号离线后一直重连失败，日志 `等待槽位超时，当前活跃: 1/1` | 密码登录占住滑块槽位且不释放 | 不要配账密；重启服务释放槽位，然后扫码 |
| 3 | 关机/断线期间的订单不自动发货；系统卡片「交易成功…等待卖家发货」也不触发 | 自动发货原先只由买家聊天「我已付款」触发，系统卡片无订单号被当成非聊天消息丢弃 | 已加系统卡片兜底：延迟 2.5 秒按 cookie+买家/会话查 10 分钟内待发货单再走同一发货路径，日志 `[兜底触发]`；关机/断线仍靠 `pending_rescue` 每 5 分钟补发 |
| 4 | 手动补发后 `item_id`/`buyer_id` 变成 chat_id | 发货成功后的平台异步回写覆盖字段（竞态），三次均发生在补发之后 | 已治标：补发成功后延迟 3 秒复读并最多补修 3 次（`[字段修复]`）；已治本：`insert_or_update_order` 写入前拦截 `item_id/buyer_id == chat_id`，日志 `[LOCAL-PATCH] 拒绝把 chat_id 写入 ...` |
| 5 | 一次给几十个买家发求花 → 私聊限制 24h | `_run_buyer_interactions` 一次拉 50 单批量发 | 关闭批量；只对新单、限速（单日 ≤3） |
| 6 | 71 条「待评价」一键评 → 风控 | 批量写接口 | 分批：每天 10–15 条，隔 1–2 小时 |
| 7 | 状态检查误报「心跳正常」 | 旧逻辑看日志文件 mtime | 已改为解析最近一条 `handle_heartbeat_response` 时间 |
| 8 | `python -c "..."` 在 PowerShell 里被吞引号 | PowerShell 解析 | 复杂脚本写成临时 `.py` 再执行 |
| 9 | bat 双击闪退/命令被拆 | LF 换行、复杂 PowerShell 引号 | bat 用 CRLF + 简单命令；需要 Shell 逻辑就写 `.ps1`/`.py` |
| 10 | ECharts 日历/热力图中出现贯穿竖线 | `visualMap` 渲染伪影 | 一律 `visualMap.show=false` + HTML 图例 |
| 11 | 日历角标改多大都看不见 | `visualMap` 默认作用于所有系列，把散点染成浅米色 | `visualMap.seriesIndex: 0`，只作用于热力图 |
| 12 | 看板 8092 起两次都「成功」 | `ThreadingHTTPServer` 的 `allow_reuse_address=1` | 启动前用 `socket.create_connection` 预探测端口 |
| 13 | 商品品类合计 ≠ 有效订单数 | `item_info` 缺新商品 | 品类统计对未匹配商品做「未识别商品」兜底 |
| 14 | CSV 在 Excel 里乱码 | 无 BOM | 已用 UTF-8 BOM + CRLF |
| 15 | 手动发货/巡检报「该账号 WebSocket 连接已断开」，但后台显示在线、心跳正常 | 心跳走 HTTP 通道；`live_instance.ws` 可能已 closed 而 `connection_state` 仍是 connected（重启后立即恢复） | `26e43fa` 先加诊断 + 等待 10 秒；`205eadd` 补 ws 看门狗：心跳循环每轮检查，陈旧 ≥30 秒则关闭旧 ws 让主循环重连（5 分钟退避防风暴），手动发货等待 5 秒未就绪会主动调看门狗。失败日志打出 `instance_id / connection_state / ws_is_none / ws_closed / ws_obj_id / registered_is_self`，仍失败就明确报错，不改判成功 |

## 9. 与「闲鱼30天作战计划」的分工建议

- **本项目负责**：账号在线、消息收发、卡券自动发货、订单补偿、经营数据与看板。
- **作战计划负责**：选品、内容/文案、上架节奏、投放与复盘；**不要复制一份本项目代码**，用第 7 节的接口消费数据。
- 若作战计划需要新字段/新接口：按第 4 节在本仓库提分支，不要另起一套。
- 若作战计划要触发发货/改订单：走后台 API（如 `/api/orders/manual-ship`，需登录 token），**不要直接写库**。
- 历史先例：合作方曾为本项目修过一个 bug，同样适用本文流程（建分支、提交、验证、回报），后续请沿用。
